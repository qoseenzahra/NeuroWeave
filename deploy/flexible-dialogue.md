# 多轮对话与流程规划的职责边界

## 问题与改动

原来的追问策略既受 Prompt 影响，也受路由代码限制：缺少前置输入容易被直接理解为补齐前置步骤，关键词和 Skill 候选可能把解释性对话提升为任务，规划校验失败后只返回错误。

现将“本轮想得到什么回答”与“哪些方法能组成经过校验的流程”分开。

1. 意图模型返回 `response_policy`：`answer`、`explore`、`inspect`、`plan`、`revise`、`clarify`。
2. `relation` 表示继续当前上下文、切换目标或独立问题，`focus` 解析“换一种”“第二种”“先只做这一步”等指代；这不是固定对话阶段。
3. 解释和讨论不进入能力树/方法图规划。模型根据 `needs_catalog`、`needs_files` 决定是否需要查询平台事实；一般概念解释可以直接回答。
4. 只有新建/修改流程进入原来的混合检索和真实输入输出契约校验。关键词、已选 Skill 和缺失输入不能覆盖有效的语义对话判断。
5. 后续修改参考数据库中的实际已选方法、参数和步骤连接。生成新的可审阅草案；原流程和运行记录不变。新草案的文件绑定仍须检查，原来的参数审阅、Dry-run、运行确认不变。
6. 切换目标不向下游注入旧流程状态。旧对话仍作为历史存在，但明确要求不继承无关目标/输入限制；当前任务契约参与后续验证。
7. 查询预算耗尽、查询失败时保留有界证据。讨论继续由回答模型说明已知与未知；不能据此断言方法/文件不存在，也不会强制重试规划。
8. 方法图校验失败时保留准确阻断原因，另外生成最多三个选项：调整目标、比较方法、准备输入或补齐平台接口。建议中的注册方法 ID 必须来自已检索目录。建议不是已生成或已执行的流程。

## 示例

| 当前消息 | 期望处理 |
| --- | --- |
| 为什么这个流程需要脑区分区？ | 解释必要性，不增补步骤 |
| 如果没有分区，还有哪些选择？ | 讨论选择与限制，不自动生成分区 |
| 对比两种算法，先不改流程 | 按需查询方法定义后比较 |
| 先看看数据集目录有什么 | 结构化只读文件查询 |
| 去掉 SIFT2 / 改用另一种方法 / 把数量改为 20000 | 根据当前实际流程生成新的草案 |
| 不做连接矩阵了，只做非 ACT 追踪 | 重新确定目标与输入范围 |
| 按你刚才第二个方案生成流程 | 解析前文指代，再检索和校验 |

这些是语义判断示例，不是按中文/英文关键词执行的规则表。

## 安全与失败策略

- `response_policy` 是后端内部字段。客户端提交的值在开始对话轮次时清空，不作为授权依据。
- 普通对话模式不生成流程卡或执行文件写操作；新策略可以帮助讨论处理方案。
- 解释、比较和澄清轮次不仅不暴露写工具，工具分发层也拒绝对应写调用；明确文件管理仍使用原来的待确认操作。
- 意图调用/结构验证最多尝试两次。失败保留低置信度，不把关键词候选当成已确认目标。
- 图校验与建议解释分离。建议模型调用失败时返回原来的准确阻断原因；不能伪造流程。
- 方法 ID 及图连接可结构验证；自然语言解释和科学建议仍需要用户审阅，不能保证模型每次分类或表达都正确。
- 本次没有新建科学算法接口；`parcellation_image` 等方法输出契约缺口依然需要单独补全，不能通过放宽 Prompt 绕过。
